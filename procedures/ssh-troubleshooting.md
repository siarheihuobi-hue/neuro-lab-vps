# Процедура: SSH не работает — разбор по ветке

Адаптировано из ранней внутренней версии чек-листа. «SSH не работает» может означать разные вещи; проверки идут **по порядку** и останавливаются на первой неудаче. После одной неудачи действие не повторяется, пока не изменился записанный факт. Секреты и адрес в отчёт не писать.

Ветки отказов (одна ветка — один следующий шаг; соседние не запускать): **панель/сайт провайдера**, **консоль панели (VNC)**, **SSH**, **движки**. Недоступность панели не означает недоступность SSH.

## Порядок проверок (место: `AGENT`, локальный терминал ноутбука; адрес берётся из пользовательского SSH config, в состояние не пишется)

1. **IP достижим?** Windows: `ping <адрес>`; macOS: `ping -c 3 <адрес>`. Нет ответа — не доказательство: многие провайдеры блокируют ICMP. Идти к шагу 2.
2. **TCP-порт SSH достижим?** Windows: `Test-NetConnection -ComputerName <адрес> -Port <порт>` (`TcpTestSucceeded`); macOS: `nc -zv <адрес> <порт>`.
   - соединение есть → сеть и порт открыты, проблема на сервере (шаги 3–5);
   - «connection refused» сразу → слушает не тот порт или sshd на другом порту (проверить порт в панели провайдера);
   - таймаут → фильтрация на стороне сети или провайдера: **с ноутбука и из сервера это не чинится**; спросить провайдера (через человека): «открыт ли входящий TCP/<порт> на этом сервере и тарифе?». Другие шаги не запускать.
3. **sshd запущен?** (нужен другой доступ: консоль провайдера) `systemctl status ssh`; не запущен → `sudo systemctl start ssh`.
4. **Локальный файрвол сервера?** `sudo ufw status`: порт SSH должен быть разрешён, иначе правило добавляется **до** включения политики deny.
5. **Аутентификация.** `ssh -v <пользователь>@<адрес>` показывает, где обрывается рукопожатие. Частые причины, от дешёвых к дорогим: неверный пользователь (root уже закрыт hardening'ом); клиент не предлагает нужный ключ (`-i`); права приватного ключа на ноутбуке (на Windows OpenSSH отвергает слишком открытые права, `bad permissions`; на macOS/Linux `chmod 600`); права `authorized_keys` (600) и `.ssh` (700) и владелец на сервере; пароль отключён, а ключ не предлагается — ожидаемое поведение после hardening.
6. Всё исключено, но сети нет → **ветка провайдера**: остановить отладку Linux; вопрос провайдеру (шаг 2).

## Консоль провайдера (VNC) и предупреждение сертификата
Недоступность консоли и предупреждение сертификата — отдельная ветка, SSH-попытки она не запускает. **Предупреждение по умолчанию не обходить.** Проверь: консоль открыта из уже авторизованной панели (не по внешней ссылке), домен в адресной строке совпадает с доменом панели. Любое сомнение — другое устройство или поддержка провайдера. Внутри консоли ничего не менять «для проверки»: нажатие там — действие на живом сервере.
