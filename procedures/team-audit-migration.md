# Процедура: аудит и перенос существующей команды (путь 8B) и сканирование каркаса

Путь 8B — для участника, у которого уже есть нейрокоманда (папки с инструкциями ролей, правилами, памятью). Источник личных данных всегда **по умолчанию остаётся дома**: переносится только то, что человек явно разрешил.

## 1. Решение человека (`HUMAN`)
Человек выбирает, что переносить: роли, правила, общие знания. Личные документы, память, дневники, клиентские и личные проекты, интеграции, ключи, токены и история чатов **по умолчанию не переносятся**.

## 2. Аудит (`AGENT`, локально, до переноса)
Искать в переносимом наборе (поиск средствами агента, не командой на сервере):
| Класс | Что искать |
|---|---|
| Секреты | заголовки приватных ключей, токены и ключи API (`sk-`, `ghp_`, `xox`, `AKIA`), строки `password=`, файлы `.env`, `known_hosts` |
| Адреса | публичные IPv4 (кроме `127.0.0.1`, `0.0.0.0`), имена хостов, адреса почты |
| Личное | имена владельца и клиентов, названия личных и клиентских проектов, ссылки на личные документы |
| Абсолютные пути | пути с буквой диска Windows, каталоги пользователя macOS (`/Users/…`), домашние каталоги Linux |
| Локальные ресурсы | ссылки на папки и интеграции, которых нет на сервере |
| Служебное | история Git (`.git/`), `.mcp.json`, `.claude/`, `.codex/`, файлы авторизации и сессий: не переносятся |
Результат — таблица находок: класс, файл, решение (убрать / заменить / оставить с причиной). **Критическая находка** (секрет, адрес, личные данные) блокирует перенос до исправления.

## 3. Адаптация под Linux
- Пути: заменить абсолютные пути Windows/macOS на относительные от корня рабочей папки.
- Разделители, регистр имён файлов, окончания строк (LF); имена файлов без пробелов и кириллицы там, где их читают скрипты.
- Инструкции, ссылающиеся на локальные инструменты ноутбука, переписать на серверные эквиваленты или пометить `[?]`.
- Роли и адаптеры: наличие файла не доказывает запуск; не переносить обещания, которых нет (skills, внешний sync, именованные агенты Claude).

## 4. Перенос с проверкой целостности
```
# на ноутбуке: архив и хеш
tar -czf team-transfer.tar.gz --exclude=.git --exclude=.mcp.json --exclude=.claude --exclude=.codex --exclude=.env --exclude='.env.*' --exclude='*.pem' --exclude='*.key' --exclude='id_*' --exclude=known_hosts --exclude='*.token' --exclude=state <папка>   # или zip; Windows: Compress-Archive с тем же исключением
sha256sum team-transfer.tar.gz               # Windows: Get-FileHash -Algorithm SHA256; macOS: shasum -a 256
# передача: scp/rsync по проектному ключу (подтверждение Manual)
# на сервере: тот же хеш; распаковка только после совпадения
```
Хеш до и после передачи должен **совпасть**; хеш хранится рядом с архивом, не внутри него. Прецедент: перенос выполнен на эталонном контуре с проверкой до и после перемещения; передача на сервер этим комплектом не проверялась `[?]`.

## 5. PASS этапа 8B
Аудит без критических находок, хеш совпал, список принятых и отклонённых находок записан в карточку (без значений секретов). `-Accept 8 -Source audit-hash -Evidence L`.

## Сканирование каркаса комплекта (перед сборкой и перед 8A)
Те же классы поиска применяются к `team-skeleton/` и ко всему комплекту; в комплекте не должно быть персональных данных владельца, клиентов, реальных проектов, авторизации, `known_hosts`, ключей, адресов и абсолютных путей. Сканирование при сборке выполняет сборщик комплекта (его скрипты в архив не входят); перед 8A агент повторяет проверку вручную по таблице выше.
