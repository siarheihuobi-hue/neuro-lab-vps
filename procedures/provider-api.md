# Провайдер и API: безопасный помощник (адаптер 1: OneDash)

> **Статус: EXPERIMENTAL.** Помощник проверен на имитации API (синтетические данные). Работа с настоящим API провайдера **не подтверждена и не проверялась**: реальная проверка имеет статус `NOT_TESTED`. Обычный маршрут через панель провайдера остаётся основным и полностью доступным. Платный маршрут по API **выключен по умолчанию** и включается только самим человеком (см. «Условие эксплуатации»).

Помощник `tools/provider-api.ps1` (Windows) и `tools/provider-api.sh` (macOS/Linux) выполняет **фиксированный набор операций** с API провайдера. Это не универсальный исполнитель запросов: операции вне набора помощник не выполняет. Если API недоступен или не подходит, маршрут продолжается через панель провайдера (ветка `PROVIDER-PANEL`); неизвестный провайдер всегда идёт этим путём. Второй провайдер (SmartApe) в комплекте работает только через панель: интеграции по API для него нет.

## Условие эксплуатации: подтверждение каждого чувствительного вызова
Безопасность платного и других чувствительных вызовов (`order-create`, `order-resolve`, `ssh-bind`) держится на том, что **движок спрашивает человека перед каждым вызовом**: в Claude режим Manual, в Codex штатные подтверждения. Постоянные разрешения, режим Bypass и широкие allowlist для этих команд недопустимы.

**Ограничение комплекта, сказанное прямо:** сам комплект не может обеспечить такое подтверждение. Это настройка движка, а не файла комплекта. Поэтому:
1. Платный маршрут **выключен по умолчанию**. Команды `order-preview`, `order-create` и `order-resolve` отвечают `ORDERS_DISABLED`, пока человек сам не выполнит в терминале `orders-enable` (интерактивный ввод слова `ENABLE`; из чата или перенаправленного ввода команда не работает). Выключить обратно: `orders-disable`.
2. Команды `order-preview`, `order-create`, `order-resolve` и `ssh-bind` отказывают, если в состоянии не записан **безопасный** режим подтверждений (`claude_permission = manual` или `codex_confirmations = default`) или записан небезопасный (`bypass`, `none`): ответы `PERMISSION_MODE_UNKNOWN` и `PERMISSION_MODE_UNSAFE`. Команды `order-status`, `order-clear`, `order-unlock`, чтение и `egress` режим не проверяют. Это проверка записанного ответа участника, а не самого движка: ответ мог быть неточным, а запись мог добавить и агент штатной командой диагностики.
3. Сам помощник и обновление комплекта маршрут не включают. **Но файл-флаг `state/provider-orders-enabled` технически может создать и агент того же пользователя**, как и обойти помощника другими средствами. Поэтому «включение человеком» — это правило процедуры и барьер от случайности, а не техническая защита: реальным условием остаётся подтверждение движком каждого чувствительного вызова. Включение на другой машине или после переустановки выполняется заново.

## Что помощник умеет и чего нет
| Команда | Что делает | Расход |
|---|---|---|
| `set-key` | человек вводит ключ в скрытом приглашении; ключ уходит в хранилище ОС | нет |
| `key-status`, `clear-key` | наличие ключа, удаление | нет |
| `auth-check`, `balance`, `list`, `orders`, `reference` | чтение, результат очищен | нет |
| `readonly-check` | авторизация, внешние адреса (семейства), каталог, число существующих серверов; ничего не покупает и не пишет | нет |
| `egress` | внешние адреса окружения (в маске); `-Window`/`--window` и `-Copy`/`--copy` показывают точный адрес только человеку | нет |
| `ssh-bind` | записывает блок `Host` для существующего сервера в пользовательский SSH-config; адрес не печатается | нет |
| `order-preview` | собирает заказ, показывает код подтверждения, **ничего не заказывает** | нет |
| `order-create` | один запрос на создание по подтверждённому предпросмотру | **да** |
| `order-status` | сверка заказов с подтверждённой операцией по идентификатору и атрибутам | нет |
| `order-resolve` | человек в терминале вводит код из окна заказа и называет нужный заказ после неоднозначной сверки (вызов инструмента без терминала отказывает; псевдотерминал или отдельное окно это обходят, см. «Принятые ограничения») | нет |
| `order-clear` | человек в терминале объявляет зависшее состояние недействительным после проверки панели | нет |
| `order-unlock` | человек в терминале снимает блокировку, оставшуюся после аварийного завершения помощника | нет |
| `orders-enable`, `orders-disable` | человек включает и выключает платный маршрут (по умолчанию выключен) | нет |

**Команд для** учётных данных сервера, смены пароля, переустановки, продления, смены тарифа и удаления нет. Любое из этого делает человек в панели провайдера.

## Ключ API
- Человек вводит ключ сам, локально, в обычном окне терминала (`set-key`). При перенаправленном вводе помощник отказывает, поэтому через штатную команду агент ключ подать не может. Ключ не попадает в чат, журналы, файлы проекта и вывод помощника, не передаётся в командной строке программы запроса.
- Хранилище: Windows — DPAPI (файл вне комплекта и проекта); macOS — связка ключей (`security`); Linux — `secret-tool` (libsecret). Если хранилища нет, помощник **отказывает**, обычный файл не создаётся. **Хранилище ОС не изолирует ключ от агента:** оно защищает файл от других пользователей и от случайного попадания в проект, но любой процесс с правами того же пользователя (в том числе команда, которую выполняет агент) потенциально может получить ключ теми же системными средствами. Дополнительная учётная запись для изоляции в комплекте **не вводится**; такое решение принимает только владелец.
- **Остаточный риск, принятый осознанно:** хранилище привязано к пользователю ОС, а не к процессу помощника. Любая другая команда, выполненная тем же пользователем (в том числе агентом в этой сессии), технически может прочитать ключ тем же способом, каким его читает помощник. Помощник ограничивает штатный путь, но не может запретить обход. Защитные слои: (1) список разрешённых адресов у ключа; (2) отдельный ключ только для чтения, если провайдер такое позволяет, для read-only проверок; (3) подтверждение инструмента на **каждый** вызов (режим Manual; `order-create`, `order-resolve`, `ssh-bind` в постоянный список разрешений не добавляются никогда); (4) лимиты и уведомления в кабинете провайдера.
- Ответ провайдера проходит **белый список** полей: значение сохраняют только известные безвредные поля (`id`, `status`, `name`, `price`, `location`, `system`, `period`, `tariff`, …); любое другое поле, в том числе массивы и вложенные объекты под ним, заменяется на `[redacted]`, а **имя** неизвестного поля заменяется на `redacted_field_N` (имя поля тоже может нести адрес или секрет). Значения внутри разрешённых полей, похожие на IPv4, IPv6, имя хоста, ссылку или длинный ключ, тоже скрываются. PowerShell Module Logging, если он включён политикой организации, может записать заголовки запросов в журнал событий: на рабочем ноутбуке его включать не нужно.

## Список разрешённых адресов (IP whitelist) и VPN
- VPN не отключается. Адрес измеряется **тем же процессом и тем же сетевым путём**, который делает запросы к API (с учётом VPN и системного proxy), по обоим семействам: IPv4 и IPv6. Строка `EGRESS` называет, что добавлять: `add_to_whitelist=ipv4`, `ipv6` или `both_v4_and_v6` (по DNS и доступности API по каждому семейству).
- Маска в выводе агента нужна только для узнавания. Точный адрес человек получает локально, без чата и журналов: `egress -Window` открывает **отдельное окно** с адресами и ждёт Enter (Windows; текст передаётся через временный файл, который окно читает и удаляет, поэтому адрес не виден в списке процессов; на macOS `--window` через Terminal не проверялось); `egress -Copy` кладёт адреса в буфер обмена; в PowerShell буфер очищается через 120 секунд, если содержимое не менялось, **но адрес всё это время виден в командной строке скрытого процесса-очистителя**; в bash-варианте буфер не очищается вообще. Буфер и список процессов читают другие локальные программы того же пользователя: надёжнее окно.
- Затем человек добавляет адрес(а) в список разрешённых адресов ключа в панели провайдера. Для операций чтения список может быть пустым, для создания, продления, переустановки и удаления он обязателен.
- Ответ `IP_NOT_ALLOWED` означает: адрес окружения не в списке. Диагностика одна: `egress`, сравнение с прежним (`CHANGED`/`UNCHANGED`), человек обновляет список. Обходов и повторов нет. Если устойчивого разрешённого адреса нет, маршрут продолжается через панель; дополнительные услуги не покупаются.

## Новый сервер в существующий маршрут подключения
`ssh-bind` берёт адрес сервера из ответа списка серверов и записывает в пользовательский файл настроек SSH (config в папке .ssh профиля) отдельный блок `Host <alias>`:
- адрес не печатается, не попадает в отчёт, журнал, состояние и проект; выводится только `address=written_not_shown`;
- существующие записи не изменяются: файл дополняется в конец, перед записью делается копия, после записи проверяется, что прежнее содержимое осталось префиксом; занятый алиас отказывает; Занятый алиас, алиас, покрытый существующим шаблоном `Host` (например, `lab*`), и дубликат в файле с окончаниями строк CRLF отклоняются; файлы, подключённые через `Include`, не просматриваются (выдаётся предупреждение); если копия не создалась, запись не выполняется.
- значение адреса проходит строгую проверку (IP или имя хоста); значения с переводом строки и лишними директивами отклоняются;
- `StrictHostKeyChecking ask`, `known_hosts` не трогается: успешный заказ **не** принимает ключ хоста; отпечаток человек сверяет с панелью провайдера на этапе 4 до первого подключения (`HOST_IDENTITY`).
Если в ответе нет известного поля адреса, помощник останавливается (`ADDRESS_FIELD_NOT_FOUND`), адрес берётся из панели.

## Покупка по API
1. Агент показывает человеку провайдера, конфигурацию, локацию, ОС, срок, количество и текущую цену тарифа (`order-preview`).
2. **Код подтверждения видит только человек:** он показывается в отдельном окне вместе с описанием заказа, в состоянии хранится только его хеш, в выводе агента кода нет. Человек подтверждает **именно этот** заказ, сообщая код; код действует 15 минут и один раз; после трёх неверных вводов предпросмотр аннулируется, а состояние `ambiguous` не аннулируется никогда: оно блокирует решение (`RESOLVE_LOCKED`) и новую покупку до тех пор, пока человек не проверит панель и не выполнит `order-clear`. Код защищает от случайной ошибки и не даёт агенту подтвердить заказ «по привычке», потому что он его не видит. Он **не** защищает от агента, который сознательно обходит помощника: файл состояния лежит рядом и не подписан, код короткий (8 шестнадцатеричных знаков), а временный файл окна доступен процессам того же пользователя в течение нескольких секунд (права только у владельца, файл удаляется окном; если окно не запустилось, помощник удаляет файл сам и предпросмотр аннулируется). Единственный надёжный барьер для траты денег — подтверждение инструмента на **каждый** вызов (см. «Ключ API», слой 3).
3. `order-create` сначала занимает блокировку (второй параллельный вызов получает `ORDER_BUSY`), затем **атомарно погашает код одноразовым маркером** `state/redeemed-…`, который никогда не удаляется: один код начинает не более одного запроса даже при потере блокировки (`CODE_ALREADY_REDEEMED`). Устаревшая блокировка **автоматически не снимается**: сообщение подсказывает человеку `order-unlock`. Затем записывается `submitted` (если запись состояния не удалась, запрос **не отправляется**: `STATE_WRITE_FAILED`) и отправляется один запрос. Ответы: `accepted` (2xx и `type=true`), `rejected` (ясный отказ 400/401/402/403/404/422, код возврата 6), иначе `uncertain` (потерянный ответ, 3xx, 409, 5xx, 2xx без `type=true`, код 4). Повреждённое или пустое состояние **блокирует** (`STATE_INVALID`), а не разрешает новый заказ.
4. При `uncertain`, `submitted` или `ambiguous` новый заказ **запрещён**, пока `order-status` не сверит заказы. Сверка идёт по идентификаторам: перед заказом сохраняется список id существующих заказов, после неопределённого результата новыми считаются только id, которых не было. Заказ принимается автоматически, только если новых заказов ровно столько, сколько подтверждено, их тариф, локация, система и срок (там, где провайдер их отдаёт) совпадают, а время создания (если отдаётся) не раньше момента отправки. Лишний заказ, расхождение, невозможность прочитать атрибуты или более раннее время создания дают `ORDER_AMBIGUOUS`: помощник ничего не выбирает, человек смотрит заказы в панели и называет нужные (`order-resolve` в интерактивном терминале, код вводится вручную). `order-status` в состоянии `ambiguous` **ничего не меняет** (даже если список заказов у провайдера изменился): выйти из него можно только `order-resolve` или `order-clear` человеком в терминале. Проверка «терминал» (ввод не перенаправлен) отсекает вызовы инструмента, но не псевдотерминал: такие команды всё равно идут только под подтверждением движка. Ограничение: полностью идентичный заказ, созданный в тот же промежуток другим способом, от нашего отличить нельзя; после сверки один раз проверьте панель.
5. Зависшее или повреждённое состояние снимает только человек в терминале: `order-clear` (после проверки панели). Удалять файл состояния вручную не нужно.
6. Реальные траты, продление, удаление и переустановка требуют отдельного подтверждения человека; наличие реализации сценария не является разрешением купить. Этап 3 по умолчанию предполагает, что оплату и регистрацию выполняет человек; путь через API необязателен и включается только явным решением человека.

## Реальная проверка только чтением (когда будет ключ)
Порядок для человека (покупок нет):
1. Если в кабинете OneDash нет аккаунта, проверка остаётся `NOT_TESTED`; покупать сервер ради неё не нужно.
2. `egress -Window`: точный адрес появится в отдельном окне; добавить его в список разрешённых адресов ключа (для чтения список может быть пустым, но если он задан, адрес обязан в нём быть).
3. `set-key`: ввести ключ в скрытом приглашении.
4. `readonly-check`: авторизация, адреса, каталог, число существующих серверов. Ожидаемое подтверждение: форма настоящих ответов (`data`, поля тарифов, заказов, поле адреса сервера).
Любой шаг с `FAIL` останавливает цепочку с понятным кодом.

## Принятые ограничения (из ревью безопасности)
- Состояние заказа и хеш кода лежат в `state/` без подписи. Агент того же пользователя может подделать файл или удалить его. Помощник отвечает на это блокировкой повреждённого состояния и отказом работать с ним (`STATE_INVALID`), но не может защититься от сознательного обхода: барьер — подтверждение инструмента на каждый вызов.
- Проверки «это человек» (`set-key`, `orders-enable`, `order-resolve`, `order-clear`, `order-unlock`, `--show`) опираются на то, что ввод и вывод не перенаправлены. Псевдотерминал (`script` и подобное) или отдельное окно с имитацией ввода это обходят, а код подтверждения человек обычно уже сообщил в чат: такие команды тоже идут только с подтверждением инструмента. Блокировка заказа не хранит владельца: если человек выполнит `order-unlock` при ещё работающем процессе, тот при выходе удалит чужую блокировку; двойной покупки это не даёт (её держит маркер погашения).
- Блокировка заказа после аварийного завершения помощника **остаётся** до `order-unlock` (автоматического снятия нет: оно позволяло двойную покупку). Код возврата 8 означает «занято или код уже погашен, ничего не отправлено», 7 — «состояние повреждено или не записывается, ничего не отправлено» (`STATE_INVALID`, `STATE_WRITE_FAILED`), 6 — «провайдер отказал», 4 — «результат неизвестен», 5 — «неоднозначно». Если состояние не удалось записать **после** отправленного запроса (`STATE_WRITE_FAILED_AFTER_REQUEST`, код 4), запрос УЖЕ ушёл: прежнее блокирующее состояние сохраняется, нужно выполнить `order-status` и ни в коем случае не заказывать повторно и не очищать состояние, не проверив панель.
- Белый список скрывает неизвестные поля, но текст внутри разрешённых полей (например, `name`) может содержать закодированный адрес или пароль в необычной форме (`203[.]0[.]113[.]5`, «root pw …»): такие значения могут пройти. Секреты хранятся вне ответов провайдера; не размещайте их в названиях.
- Время создания заказа: bash сравнивает ISO-строку в UTC (значения со смещением и других форматов не проверяются), PowerShell разбирает дату вместе со смещением; реализации здесь расходятся.

## Что подтверждено, что нет
- Проверено на локальной имитации API (синтетические данные): ключи, очистка ответов, коды ошибок, предпросмотр, подтверждение, единичность запроса, сверка после потери ответа по идентификаторам, неоднозначные случаи, привязка адреса к SSH-config (IPv4, IPv6, враждебное значение), показ точного адреса только человеку, read-only проверка.
- **Не проверено** на настоящем API: форма ответов (`data`, поля тарифов, заказов, поле адреса в списке серверов), реальная работа списка разрешённых адресов, асинхронное создание сервера, окно показа на macOS. Адаптер строился по публичной документации API 2.0; создание сервера в ней не принимает SSH-ключ и cloud-init, поэтому после создания первичный доступ по-прежнему настраивается этапом 4 (пароль сервера человек получает в панели провайдера; помощник его не запрашивает).
