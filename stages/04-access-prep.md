# Этап 4. Первоначальная подготовка доступа

Обязательный явный этап **до** Remote-SSH. Четыре факта независимы: отпечаток хоста (`HOST_IDENTITY`), ключ создан и пригоден (`KEY_READY`), публичный ключ установлен (`KEY_INSTALLED`), вход по ключу работает (`KEY_LOGIN`). «Ключ создан» не засчитывается как «установлен» или «вход работает».

**Вход:** этап 3 PASS (сервер получен), есть первичный доступ (пароль входа от провайдера). Обычный пользователь и проектный ключ — результат этого этапа.

## Подсказки до первого ввода пароля (показать целиком)
- Терминал: VS Code → меню «Терминал» (при скрытом меню через «…»); для ОС участника.
- Пароль при вводе не показывается — это нормально. Вставить **один раз** и нажать Enter; несколько вставок дают неверный пароль.
- Перед каждым приглашением агент называет **чей это пароль и для какого действия**: пароль входа на сервер от провайдера; пароль `sudo` текущего обычного пользователя; фраза защиты ключа. Это три разных секрета.
- Пароль, IP и ключи не отправлять в чат; на скриншоте скрыть. Раскрытый пароль меняет владелец.
- Первый вход по паролю делает **человек** (`HUMAN-LOCAL-TERMINAL`).

## Шаги
| № | Место | Действие | Доказательство |
|---|---|---|---|
| 4.0 | `HUMAN-LOCAL-TERMINAL` + `PROVIDER-PANEL` | первое подключение; **полный** отпечаток хоста (ED25519), показанный клиентом, сверяется с независимым каналом (панель или консоль провайдера) целиком, а не по началу и концу; затем проектный `known_hosts` и `StrictHostKeyChecking=ask` | `HOST_IDENTITY=PASS` (человек подтвердил совпадение, `U`) |
| 4.A | `AGENT` | пригодность ключа **до** установки на сервер (ниже), при необходимости новый проектный ключ ED25519 на ноутбуке; приватный ключ остаётся на ноутбуке | `KEY_READY=PASS` (`ssh-keygen` читает ключ, отпечаток публичной части записан в карточку; отпечаток — не секрет) |
| 4.B | `HUMAN-LOCAL-TERMINAL` (пароль) | на сервере создан **обычный пользователь**; его `authorized_keys` содержит ровно этот публичный ключ; права `.ssh` 700 и `authorized_keys` 600; команды готовит агент | `KEY_INSTALLED=PASS` (отпечаток в `authorized_keys` на стороне сервера совпал) |
| 4.C | `AGENT` | **отдельный** вход по ключу под обычным пользователем: `BatchMode=yes`, пароль и keyboard-interactive отключены, строгая проверка хоста | `KEY_LOGIN=PASS` (`whoami` вернул обычного пользователя, код выхода 0, пароль не запрашивался; метка `L`) |

Имя пользователя берётся из выбора человека и записывается в его пользовательский SSH-config, а не в состояние и не в отчёты; не предполагай имя из прежних прогонов или документов.

## Личность хоста (4.0): три исхода, одно решение на конкретный хост
- **VERIFIED:** полный отпечаток совпал с независимым каналом → `-Fact HOST_IDENTITY=PASS -Source panel-fingerprint -Evidence U`.
- **UNVERIFIED:** независимой сверки сейчас нет (панель недоступна, консоль не отвечает). Это честное состояние, оно не блокирует всё навсегда.
- **ACCEPTED_RISK:** человек явно решил продолжить без сверки для этого конкретного хоста → `-Fact HOST_IDENTITY=ACCEPTED_RISK -Source owner-decision -Evidence U`. Это решение **не** превращается в VERIFIED: в итоге остаётся пометка «отпечаток не подтверждён независимо», а агент не пишет «сервер независимо подтверждён».
- **Изменившийся или неизвестный после принятия ключ хоста — всегда СТОП**, согласие на прежний ключ его не покрывает.
- Повторная сверка нужна только при конкретном изменении: новый сервер (новое поколение), переустановка ОС, предупреждение клиента об изменении ключа хоста, сообщение провайдера о пересборке или переносе сервера на другой хост (в том числе при смене тарифа). Обычная перезагрузка или смена тарифа на том же хосте и с той же ОС не повод.

## Консоль провайдера (VNC): отдельная ветка
Основной маршрут — SSH. Консоль нужна для независимой сверки отпечатка или восстановления. Если консоль не принимает клавиатуру, обрывается по таймауту или показывает предупреждение сертификата: одна диагностика, **без повторных входов по кругу и без автопрохода предупреждения TLS**; затем один альтернативный путь из разрешённых (другой браузер или устройство, поддержка провайдера, исход ACCEPTED_RISK по решению человека). Все слои раздельны: панель, консоль, SSH, личность хоста, движки.

## Пригодность ключа (4.A) до установки
1. Агент ищет проектный ключ в пользовательской папке SSH по именам и метаданным; содержимое приватного ключа не читает и не печатает.
2. Проверка читаемости: `ssh-keygen -y -P "" -f <ключ>` выводит публичную часть (код 0), значит фраза не нужна; при ошибке ключ защищён фразой или повреждён.
3. Если фраза нужна и человек её **не знает**: не угадывать, не перебирать. Создаётся **отдельный** проектный ключ ED25519, старый ключ остаётся нетронутым. Защиту нового ключа (без фразы или с фразой, которую вводит сам человек) выбирает человек осознанно.
4. Возраст ключа не причина его отвергать; один ключ может использоваться на нескольких серверах. В команде для нового сервера используется публичная часть выбранного проектного ключа, а не ключ прежнего сервера.

## Права и повторы
- Права обычного пользователя: членство в группе `sudo`; **passwordless sudo не настраивается** (NOPASSWD запрещён). Для административных операций пароль sudo вводит человек; `sudo -v` в терминале человека не даёт агенту права администратора (см. этап 6).
- Если проектный ключ отвергнут: **одна** диагностика «почему отклонён ключ» — права и владелец файла приватного ключа на ноутбуке (Windows OpenSSH отвергает слишком открытые права: `bad permissions`), установленный публичный ключ, права `authorized_keys`. Не перебирать варианты.
- Пароль входа: одна неудача — стоп. Новый кандидат, который человек вспомнил, — новая причина: **одна** согласованная попытка, пароль вводит сам человек; число попыток записывается. Срок блокировки не выдумывай.
- Raw-вывод SSH с адресом в состояние не писать.

**PASS:** все четыре факта записаны каждый со своим доказательством (для `KEY_LOGIN` метка с `L`), затем `-Accept 4 -Source key-user-login -Evidence LU`. Скрипт откажет, если факты не записаны.

**Ошибка:** ветка SSH (см. `procedures/ssh-troubleshooting.md`), записать, какая из проверок не прошла и число попыток.

Статус референса: key-only вход для root и обычного пользователя подтверждён на одном контуре. Независимого прогона другим человеком нет `[?]`.

## Четыре контрольные точки доступа (правило 20)
`HOST_IDENTITY` → `SSH_AUTH` → `ADMIN_ACCESS` → `RECOVERY`: `-Checkpoints` показывает состояние каждой. `SSH_AUTH` ставится по входу по ключу в **процессе агента** (`-Fact SSH_AUTH=PASS ... -Evidence L`; прежний `KEY_LOGIN` засчитывается как совместимый источник). Вход человека в консоль провайдера или в свой терминал `SSH_AUTH` не доказывает. `RECOVERY=PASS` требует `-Scope agent_channel` (агент сам может восстановить доступ) либо `-Scope human_only` (только человек через консоль провайдера) и честно называется в итоге. Сравнение отпечатков и ввод в консоль: `procedures/console-help.md`. Различай: «консоль человека работает», «агент имеет SSH», «агент имеет sudo» — три разных факта. Две неудачные попытки по одной области без нового знания останавливают круг (правило 21).
